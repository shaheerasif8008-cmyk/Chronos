# Chronos vs ChatGPT / Claude — Performance Gap Analysis

**Date:** 2026-07-02
**Branch:** `claude/chronos-performance-comparison-lqrlx2` (tip of `main` @ `c66226a`)
**Method:** code audit of the quality-determining runtime paths (`core/llm.py`, `runtime/agent_loop.py`, `runtime/tool_registry.py`, `core/context.py`, `core/intent.py`, `routers/chat.py`, `core/config.py`, `core/prompts/base_system_prompt.md`), cross-referenced against `docs/LAUNCH_READINESS_AUDIT.md` and `docs/chronos_total_parity_matrix.md`.

---

## What question this document answers

The launch audit answers *"can we deploy this?"* The parity matrix answers *"which features exist?"* This document answers the harder question: **why does using Chronos still feel far behind ChatGPT and Claude, even though most of the feature checkboxes are filled in** — and what, specifically, closes that gap.

The short answer: **the gap is not feature count.** The parity matrix shows genuine breadth — chat, tasks, research, artifacts, memory, browser/computer operation, connectors, schedules, agents. The gap is in five compounding places, ranked below by how much of the felt difference each one explains. The first two are the big ones, and both are cheaper to fix than any feature row in the matrix.

---

## Gap 1 — The model quality ceiling (largest single factor)

Every answer Chronos produces is generated by a mid-tier model. No amount of harness, memory, or governance work can make a mid-tier model's answer read like a frontier model's answer — and users comparing Chronos to ChatGPT/Claude are comparing directly against frontier output.

**Evidence in code:**

- The chat model registry tops out at `gpt-5.4-mini` — a *mini*-class model — and it is labeled **"Best"** in the UI (`apps/api/core/llm.py:35-44`). The other options are `gpt-5.4-nano`, `deepseek-v4-pro`, and `deepseek-v4-flash`. There is no frontier-class entry at all.
- The agent loop (task execution — the "does the work" path the whole product pitch rests on) defaults to `deepseek-v4-pro` (`apps/api/core/config.py:43`).
- The difficulty-escalation ladder — the mechanism that steps up to a stronger model "when the loop is struggling" — also tops out at `gpt-5.4-mini` (`apps/api/core/llm.py:160-165`). When Chronos is struggling, its ceiling is another vendor's mini model.
- Everything routes through a **single provider** (OpenRouter — `model_kwargs()` at `llm.py:268-279`), and the last-resort fallback is a free-tier model (`openrouter/minimax/minimax-m2.5:free`, `config.py:35`). The launch audit already flagged the default model IDs as unverified (B6).

**Why this dominates:** ChatGPT serves the full GPT-5.x line and Claude.ai serves the Claude 5 family / Opus 4.8. The user's mental benchmark *is* frontier output — depth of reasoning, writing quality, tool-call judgment, recovery from ambiguity. Chronos's excellent system prompt (`base_system_prompt.md` is genuinely well-written) is being executed by models that can't fully honor it.

**Fix (small effort, largest payoff):**

1. Add a true frontier tier to `CHAT_MODEL_OPTIONS` and make it the default for `difficulty in {"standard","hard"}` and for all agent-loop execution. Current frontier options and list pricing: Claude Opus 4.8 (`claude-opus-4-8`, $5/$25 per MTok, 1M context), Claude Sonnet 5 (`claude-sonnet-5`, $3/$15, near-Opus on agentic/coding work), GPT-5.x full-size via OpenAI. Keep the nano/flash tier for routing/extraction only.
2. Add direct provider support (Anthropic/OpenAI APIs) alongside OpenRouter, with per-org BYOK — the `.env` already anticipates this (`BACKUP_API_KEY`) and litellm supports it natively. Single-provider dependence is both a quality and an availability risk.
3. Extend `_AGENT_STRENGTH_ORDER` so escalation actually escalates: `flash → nano/haiku → sonnet-class → opus-class`.
4. Route by task value, not just difficulty: sub-agents and extraction on cheap models, the main agent loop and final synthesis on the frontier model. This is how the competitors keep frontier quality affordable.

Without this change, every other improvement in this document raises the floor but not the ceiling.

## Gap 2 — Latency and token economics (the "it feels slow" factor)

ChatGPT and Claude feel instant because their serving stacks are built around prompt caching and minimal pre-stream work. Chronos re-pays full price — in both latency and tokens — on every single model call.

**Evidence in code:**

- **Zero prompt caching anywhere.** No `cache_control`, no caching configuration in `llm.py`, `agent_loop.py`, or `chat.py` (grep confirms). Anthropic/OpenAI cache reads cost ~0.1× and dramatically cut time-to-first-token; Chronos never gets either benefit.
- **The per-call payload is enormous and fully re-sent every iteration.** Each inline chat turn ships `INLINE_CHAT_TOOLS` — roughly **85–90 full JSON tool schemas** (browser operator suite, Composio connectors, computer, Canva, the 10-tool doc suite, image/voice/data, repo tools…) (`apps/api/runtime/tool_registry.py:1311-1349`) — plus the ~300-line system prompt, org context files, retrieved memories, and skill content. The agent loop does this up to `MAX_ITERATIONS = 40` times per task (`agent_loop.py:62`) against a 120K context budget (`config.py:231`). Uncached, that is tens of thousands of redundant input tokens per iteration, at full price, with full prefill latency.
- **Pre-stream work gates the first token.** Every non-trivial chat turn runs `classify_request()` (a fast-model LLM round trip, `core/intent.py:114`) in parallel with `assemble_context()` — which itself runs skill-relevance matching and a memory embedding call (`core/context.py:129-193`). Parallelizing them was the right move (`routers/chat.py:717-727`), but the first token still waits on the slower of an LLM call and an embedding call, every turn. ChatGPT starts streaming almost immediately.
- **Retry logic only retries rate limits.** `_with_retry` catches only `litellm.RateLimitError`; `_RETRYABLE_STATUS_CODES = {429, 500, 502, 503, 504}` is defined and never used (`llm.py:20,89-98`). Transient 5xx/timeout errors — the most common provider failures — surface to the user immediately instead of being retried. `complete_json` even runs its primary attempt with `max_retries=0` (`llm.py:483`).

**Fix (ordered by payoff per effort):**

1. **Enable prompt caching.** Structure every call as stable-prefix-first (tools → system prompt → org context → history, volatile content last) and mark cache breakpoints. litellm passes `cache_control` through to Anthropic; OpenAI/OpenRouter cache automatically on stable prefixes. Two invariants to enforce: never interpolate timestamps/request IDs into the system prompt, and keep the tool list byte-identical between iterations. For an agent loop re-sending 50K+ tokens 40 times, this is a ~10× input-cost reduction and the single biggest TTFT win available.
2. **Cut the tool payload per turn.** ~90 schemas is 3–4× past the point where tool-selection accuracy degrades for mid-tier models, and it's pure prefix weight. Options: mode/intent-scoped tool subsets (the mode registry already exists), or a deferred-loading pattern — send a small core set plus a `tool_search` tool that pulls in additional schemas on demand (schemas get *appended*, preserving the cache prefix). This improves quality (Gap 1) and latency simultaneously.
3. **Heuristic-first routing.** `_heuristic_classify` already exists and is decent (`intent.py:98`). Invert the order: classify heuristically, stream immediately, and only pay an LLM classification for genuinely ambiguous messages. Cache skill-relevance results per conversation instead of recomputing per message.
4. **Fix the retry seam.** Retry on the already-defined status-code set with backoff, not just `RateLimitError`.

## Gap 3 — Degraded-by-default: the demo-product problem

A user who connects Chronos and asks it to *do* something frequently hits a placeholder, a fixture, or a truthful-but-useless "degraded" response. ChatGPT never does this — every advertised capability is live. The parity matrix's honesty discipline ("honest degraded" rows) is the right engineering ethic but the wrong user experience for a product claiming to compete.

**Evidence:**

- Vision OCR, image generation, image editing, STT, and TTS are all **disabled by default** — their model IDs default to empty strings (`config.py:50-53`). The multimodal parity rows are "Done (honest degraded)": the code paths exist, but a default install can't see an image or generate one.
- Browser defaults to fixture tier without Tavily/Chromium; Gmail defaults to demo mode; `gmail.send` is permanently blocked (launch audit F1, F3, S4). The audit's own words: "several advertised capabilities are demo/fixture or disabled out of the box."
- The connector-framework queue never drains in the shipped production manifest because no worker service is deployed (B2), and intra-org authorization is off without OpenFGA (B3).

**Fix:** define one **reference production configuration** where every capability shown in the UI is live, and enforce it: a startup "live-only" guard in production that refuses to boot (or visibly disables the surface) when a capability's provider isn't configured, rather than silently degrading mid-task. Wire the multimodal model IDs to real defaults (e.g. vision → the vision-capable chat model already in the registry; a real image/STT/TTS provider). Ship the worker + OpenFGA + pgvector deployment fixes from the audit's critical path — they are prerequisites for "it just works."

## Gap 4 — Reliability is proven in CI, not in production conditions

The Phase-1 reliability engineering (queueing, cancellation, recovery, dead-letter, idempotency, trace replay) is real and well-tested — but almost entirely against the happy path, in a single process, with behavioral E2E gated off.

**Evidence:**

- Behavioral E2E (real model, real flows) only runs when `OPENROUTER_API_KEY` is present in CI secrets; otherwise skipped — so the flows users actually exercise are not continuously proven (audit F2).
- The audit's coverage assessment: thin on provider outage, Redis eviction mid-flight, worker crash mid-job, OAuth refresh against a live IdP, scheduler duplication under multi-instance (§Phase 5). These are precisely the failure modes that make a product feel unreliable in week two.
- Single-process runtime: scheduler and task runner live in the web dyno (B4); free Redis with `allkeys-lru` silently evicts rate-limit/idempotency/vault-cache state (B7); workflow recovery is default-tenant-only (B5).
- Code-quality smells in the hottest file: `stream_step` is **defined twice** in `core/llm.py` (lines 347 and 407 — the second silently shadows the first; one is dead code), and the dead `_RETRYABLE_STATUS_CODES` constant noted above. Small, but they signal that the most quality-critical file isn't getting the review pressure it needs.

**Fix:** un-gate behavioral E2E as a required nightly (a few dollars of model spend per night is the cheapest reliability instrumentation available); add the audit's missing failure-mode tests as the P2 hardening block; execute launch blockers B1–B7 per the audit's critical path; delete the duplicate `stream_step` and wire the retryable-status set into `_with_retry`.

## Gap 5 — Breadth over depth in the product surface

Many parity rows are implemented at the "backend + static UI guard" level. The competitors' equivalents are deeply polished daily-driver surfaces.

Highest user-visible depth gaps, in order:

| Surface | Chronos today | Competitor bar |
|---|---|---|
| Long-running task console | Partial task/activity UI; "complete console missing" (matrix, Manus-style row) | Manus-grade live plan + actions + artifacts + pause/resume in one view — this is the product's core pitch, it should be the flagship screen |
| Global search UI | Backend done, UI pending (matrix) | Cmd-K everywhere |
| Shared conversations / collaboration UI | Comments backend done, UI pending; sharing missing | One-click share links, live collaboration |
| Notifications | Missing/partial | Approval/task/monitor pushes across in-app, email, Slack, mobile |
| Mobile web | Unknown/incomplete | Full-parity responsive + native apps |
| Source viewer / project knowledge UX | Viewer missing | Claude Projects-grade source inspection and citation click-through |

**Fix:** stop opening new capability rows until the task console, global search, and notifications reach daily-driver depth. One deeply excellent execution surface beats three more "honest degraded" capabilities for perceived parity.

## What would actually close the gap — sequenced plan

Ordered by felt-improvement per engineering week. Weeks 0–2 are mostly configuration and focused changes, and deliver more perceived improvement than any feature quarter to date.

**Weeks 0–2 — model + speed (Gaps 1, 2):**
1. Add frontier model tier (Opus-class + Sonnet-class), make it the agent-loop and hard-difficulty default; extend the escalation ladder; add direct-provider BYOK.
2. Enable prompt caching with stable-prefix call construction.
3. Cut per-turn tool schemas via mode-scoped subsets or deferred tool loading.
4. Heuristic-first intent routing; cache skill relevance per conversation.
5. Fix `_with_retry` to cover 5xx/timeouts; remove the duplicate `stream_step`.

**Weeks 2–6 — live-by-default + deployability (Gaps 3, 4):**
6. Reference production config: worker service, OpenFGA, pgvector-capable Postgres, persistent Redis, verified model IDs (audit B1–B7 critical path).
7. Live-only production guard; wire vision/image/voice model defaults; resolve `gmail.send` (post-approval send or remove from surface).
8. Nightly behavioral E2E as a required check.

**Weeks 6–12 — reliability depth + product depth (Gaps 4, 5):**
9. Failure-mode test block: provider outage, Redis eviction, worker crash mid-job, multi-instance scheduling, OAuth refresh.
10. Task console to Manus-grade; global search UI; notifications.

## Making "performance vs ChatGPT" measurable

Today the comparison is vibes. Add a small benchmark harness (CI job + dashboard) so every change above is scored:

- **Latency:** time-to-first-token and tokens/sec for a fixed set of 10 chat prompts (trivial → hard), tracked per commit.
- **Task success:** ~20 canonical end-to-end tasks (research with citations, doc creation, data analysis, browser form-fill, multi-step agent task) scored pass/fail by a rubric grader; report success rate and cost per completed task.
- **Cost:** input/output tokens and $ per task, with cache-hit rate once caching lands (a near-zero cache-read rate is the regression alarm for silent prefix invalidators).
- **Reliability:** nightly behavioral E2E pass rate; recovery drills (kill worker mid-task) on a schedule.

Once these numbers exist, "not even close to ChatGPT" becomes a set of tracked deltas — and the first two gap fixes should move all four dials within a sprint.

## What is *not* the problem

Worth stating plainly, because it changes where effort goes: **the architecture is not the gap.** The three seams are real and centrally enforced, tenant isolation is proven at multiple layers, the audit log is genuinely immutable, the vault is correct, the agent loop is a real native tool loop with parallel calls, compaction, injection gating, and durable replay. This is a better governance foundation than most products in the category. The gap is the engine inside the well-built chassis (Gap 1), the drivetrain losses (Gap 2), and the fact that the car ships with the fuel line disconnected (Gap 3).
